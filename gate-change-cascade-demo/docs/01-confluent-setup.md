# Doc 01 — Confluent Cloud & MCP Setup

**Gate Change Cascade Demo — Step 1**

This guide sets up your Confluent Cloud environment, cluster, Schema Registry, Flink compute pool,
and the Confluent MCP server in Bob. All setup steps have a **Bob MCP prompt** alternative —
use those instead of the UI wherever possible to demonstrate the MCP capability.

---

## Prerequisites

- Confluent Cloud account (free tier works — promo code `CONFLUENTDEV1` bypasses the credit card)
- Python 3.11+ installed locally
- Node.js v22+ installed (for the Confluent MCP server)
- IBM Bob installed locally with the Confluent MCP server configured (see Step 1.5)
- `git clone` this repo and `cd usecases/gate-change-cascade`

   - Type: **Basic**  |  Provider: **AWS**  |  Region: `us-east-2`

## Step 1.2 — Retrieve Credentials and Populate `.env`

```bash
cp .env.example .env
```

Collect each value below from the Confluent Cloud UI and paste into `.env`:

| `.env` Variable | Where to find it |
|---|---|
| `CONFLUENT_CLUSTER_ID` | Cluster overview → ID (`lkc-XXXXX`) |
| `CONFLUENT_BOOTSTRAP_SERVERS` | Cluster overview → Bootstrap server (`pkc-XXX.<region>>.aws.confluent.cloud:9092`) |
| `CONFLUENT_ENVIRONMENT_ID` | Environment → Details panel → ID (`env-XXXXXX`) |
| `KAFKA_API_KEY` / `KAFKA_API_SECRET` | Cluster → API keys → Add key → **My account** → cluster-scoped |
| `CONFLUENT_API_KEY` / `CONFLUENT_API_SECRET` | Admin → API keys → Add key → **Global** scope |

> ⚠️ **`KAFKA_API_KEY` must be cluster-scoped** (created from inside the cluster, not Admin). The simulator uses SASL/PLAIN and requires a cluster-scoped key.

## Step 1.3 — Schema Registry

Schema Registry is required by three parts of this demo:

- **Flink SQL** — automatically registers and looks up schemas when reading from or writing to
  Kafka topics. The `flight-events` JSON schema and the `ops-alerts` schema (generated by
  the anomaly detection job) are both stored here.
- **TableFlow** — requires a registered value schema on `ops-alerts` before it can start syncing
  to Iceberg. Without Schema Registry, TableFlow cannot determine the table structure.
- **Confluent MCP tools** — `list-schemas`, `search-topics-by-tag`, and related tools query
  Schema Registry directly, using the `baseUrl` you provide at call time.

> 💡 Schema Registry is provisioned automatically with your Confluent Cloud environment under
> the **Essentials** Stream Governance package — no separate creation step is needed. You just
> need to copy the endpoint and create an API key.

1. In your environment left sidebar click **Schema Registry** → **Endpoints** → copy the Public Endpoint
2. Click **API keys** → **Add API key** (SR-scoped)

   Paste into `.env`:
   ```env
   CONFLUENT_SCHEMA_REGISTRY_URL=https://psrc-XXXXX.<region>.aws.confluent.cloud
   CONFLUENT_SR_API_KEY=<16-char key>
   CONFLUENT_SR_API_SECRET=<64-char secret>
   ```

## Step 1.4 — Flink Compute Pool

A **Flink Compute Pool** is a managed pool of compute resources (measured in **CFUs —
Confluent Flink Units**) that runs your Flink SQL statements. Think of it as the engine that
executes queries against your Kafka topics in real time.

In this demo the compute pool runs the anomaly detection job (`gate-change-anomaly-detection`),
which reads from `flight-events`, applies a 10-second tumbling window with `AI_DETECT_ANOMALIES`,
and writes detected anomalies to `ops-alerts` — continuously, as long as the pool is running.

Key points:
- **CFUs are consumed only while statements are running** — a pool at rest costs nothing
- **Max CFUs: 5** is sufficient for this demo (one streaming INSERT job)
- The pool must be in the **same region as your Kafka cluster** — cross-region Flink is not supported
- `FLINK_REST_ENDPOINT` is the regional Flink REST API base URL — used by the MCP server to
  submit and manage statements programmatically

1. In your environment click **Flink management** → **Compute pools** → **Add compute pool**
2. Provider: **AWS** | Region: **same as cluster** | Name: `gcc-pool` | Max CFUs: `5`
3. Click **Create** — wait ~2 min for **Running** status

   Paste into `.env`:
   ```env
   FLINK_COMPUTE_POOL_ID=lfcp-XXXXX
   FLINK_REST_ENDPOINT=https://flink.<region>>.aws.confluent.cloud
   FLINK_ORG_ID=<your org UUID — User Settings → Organization ID>
   ```

> 💡 `FLINK_ORG_ID` is your Confluent Cloud organization UUID — find it under
> **User menu (top-right)** → **Organization settings** → **Organization ID**.

## Step 1.5 — Set Up the Confluent MCP Server in Bob

The Confluent MCP server lets you drive all Confluent Cloud operations — topic creation,
Flink SQL deployment, schema inspection — directly from Bob prompts instead of the UI.
Set this up now so you can use Bob for Steps 1.6 onward.

### 1.5.1 — Install Node.js v22

```bash
# Install nvm if not already present
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
source ~/.zshrc   # or ~/.bashrc

# Install and activate Node 22
nvm install 22
nvm use 22
node --version    # should show v22.x.x

# Install other prerequisites (macOS)
brew install openssl zstd
```

### 1.5.2 — Install the Confluent MCP package

```bash
PATH="/opt/homebrew/bin:$PATH" npm install -g @confluentinc/mcp-confluent
```

### 1.5.3 — Find the installed paths

You need two paths for the Bob config:

```bash
# Path to the node binary
which node
# e.g. /Users/you/.nvm/versions/node/v22.14.0/bin/node

# Path to the MCP server entry point
ls $(npm root -g)/@confluentinc/mcp-confluent/dist/index.js
# e.g. /Users/you/.nvm/versions/node/v22.14.0/lib/node_modules/@confluentinc/mcp-confluent/dist/index.js
```

### 1.5.4 — Add to `~/.bob/settings/mcp.json`

Open (or create) `~/.bob/settings/mcp.json` and add the `confluent` block.
Replace all `<placeholders>` with your values from Steps 1.2–1.4 and the paths from Step 1.5.3.

> 💡 **Schema Registry `baseUrl`:** The Confluent MCP tools for Schema Registry
> (`list-schemas`, `search-topics-by-tag`, `search-topics-by-name`, etc.) require the
> Schema Registry endpoint passed as a `baseUrl` parameter at call time — they do **not**
> read `SCHEMA_REGISTRY_URL` from the env automatically. The easiest way to pass it is to
> tell Bob your SR URL once per session:
> ```
> My Schema Registry URL is https://psrc-XXXXX.us-east-1.aws.confluent.cloud — use it for all Schema Registry calls
> ```
> Bob will include `baseUrl` in every subsequent SR tool call automatically.
>
> Alternatively, reference `CONFLUENT_SCHEMA_REGISTRY_URL` from your `.env` explicitly
> in each Bob prompt that involves schemas.

```json
{
  "mcpServers": {
    "confluent": {
      "command": "/Users/you/.nvm/versions/node/v22.14.0/bin/node",
      "args": [
        "/Users/you/.nvm/versions/node/v22.14.0/lib/node_modules/@confluentinc/mcp-confluent/dist/index.js"
      ],
      "env": {
        "BOOTSTRAP_SERVERS": "<your CONFLUENT_BOOTSTRAP_SERVERS>",
        "KAFKA_API_KEY": "<your KAFKA_API_KEY>",
        "KAFKA_API_SECRET": "<your KAFKA_API_SECRET>",
        "SCHEMA_REGISTRY_URL": "<your CONFLUENT_SCHEMA_REGISTRY_URL>",
        "SCHEMA_REGISTRY_API_KEY": "<your CONFLUENT_SR_API_KEY>",
        "SCHEMA_REGISTRY_API_SECRET": "<your CONFLUENT_SR_API_SECRET>",
        "CONFLUENT_CLOUD_API_KEY": "<your CONFLUENT_API_KEY>",
        "CONFLUENT_CLOUD_API_SECRET": "<your CONFLUENT_API_SECRET>",
        "FLINK_API_KEY": "<your CONFLUENT_API_KEY>",
        "FLINK_API_SECRET": "<your CONFLUENT_API_SECRET>",
        "FLINK_ENV_ID": "<your CONFLUENT_ENVIRONMENT_ID>",
        "FLINK_ORG_ID": "<your FLINK_ORG_ID>",
        "FLINK_COMPUTE_POOL_ID": "<your FLINK_COMPUTE_POOL_ID>",
        "FLINK_REST_ENDPOINT": "<your FLINK_REST_ENDPOINT>",
        "FLINK_CATALOG_NAME": "<your Confluent environment name>",
        "FLINK_DATABASE_NAME": "cluster-gcc"
      }
    }
  }
}
```

> 💡 `FLINK_API_KEY` / `FLINK_API_SECRET` use the same **Global** key as `CONFLUENT_CLOUD_API_KEY` /
> `CONFLUENT_CLOUD_API_SECRET` — you do not need a separate Flink key.
>
> 💡 `FLINK_CATALOG_NAME` is the name of your Confluent Cloud **environment** (e.g. `gate-change-cascade`).
> `FLINK_DATABASE_NAME` is the **Kafka cluster name** within that environment (e.g. `cluster-gcc`).
> These two values are used as the default catalog and database for all `create-flink-statement` calls,
> so you don't need to specify them explicitly each time.

### 1.5.5 — Verify the connection in Bob

1. Open Bob → **Settings** (top-right gear icon) → **MCP**
2. Search for `confluent` — the server should show a green **Connected** status
3. If it shows an error, double-check the `command` path and that the `env` values are filled in

> ⚠️ If the server shows **Failed to connect**, run the node command manually to see the error:
> ```bash
> node <path-to-index.js>
> ```
> Common issues: wrong node path, missing `openssl`/`zstd`, or empty env vars.

## Step 1.6 — Create Kafka Topics

A **Kafka topic** is a named, ordered log of messages — producers write to it, consumers read from it. Topics are the backbone of all data flow in this demo: the simulator writes flight metrics to `flight-events`, Flink reads from it and writes anomalies to `ops-alerts`, and the alert consumer reads from `ops-alerts` to trigger the WXO agent.

Only two topics are needed for this use case.

### Using Bob (MCP)

Prompt Bob:
```
Create topics 'flight-events' and 'ops-alerts' with 6 partitions each
```

Tool called:
```text
mcp__confluent__create-topics
  { "topicNames": ["flight-events", "ops-alerts"] }
```

Verify:
```
List topics in my Confluent cluster
```
```text
mcp__confluent__list-topics
```

### Using Confluent Cloud UI

Topics → **Add topic** → create each with 6 partitions, `cleanup.policy=delete`:

| Topic | Purpose |
|---|---|
| `flight-events` | Simulator produces schedule metrics here |
| `ops-alerts` | Flink writes anomaly detections here |

## Step 1.7 — Start the Simulator and Verify

`bash app-run-local.sh` starts four processes together:

| Process | What it does |
|---|---|
| **Simulator control server** | HTTP API on `localhost:8090` — lets the dashboard and CLI inject anomalies or pause/resume the stream |
| **Flight events producer** | Continuously generates synthetic flight metrics (gate_wait, departure_delay, turnaround_time) and writes them to the `flight-events` Kafka topic |
| **Alert consumer** | Reads detected anomalies from `ops-alerts` and dispatches each one to the WXO `supervisor_agent` — this is the bridge between Flink and the agent pipeline |
| **Streamlit dashboard** | Web UI at `http://localhost:8080` — shows live flight metrics, agent activity, and provides controls to inject anomalies |

This doc lives in `docs/` — all commands below must run from the **`gate-change-cascade/`** root.

```bash
# Navigate to the use case root (from anywhere in the repo)
cd "$(git rev-parse --show-toplevel)/usecases/gate-change-cascade"

# Set up Python virtual environment for the simulator + dashboard
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# Start the demo (producer + alert consumer + Streamlit dashboard)
bash app-run-local.sh
```


Open [http://localhost:8080](http://localhost:8080) and click **▶ Start Stream**.

Verify with Bob:
```
List schemas in my Schema Registry — baseUrl is https://psrc-XXXXX.us-east-1.aws.confluent.cloud
```
```text
mcp__confluent__list-schemas
  { "baseUrl": "https://psrc-XXXXX.us-east-1.aws.confluent.cloud" }
```
You should see `flight-events-value` appear within ~10 seconds of starting the simulator.

> 💡 Replace `psrc-XXXXX…` with your `CONFLUENT_SCHEMA_REGISTRY_URL` value from `.env`.
> Once you give Bob your SR URL in a prompt, it will reuse it for all subsequent SR tool calls
> in the same session.
